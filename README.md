# Trip Service

Сервис поездок для лабораторных по Go. Позволяет создать и завершить поездку,
сохранить координаты и посмотреть маршрут. Данные хранятся в PostgreSQL.
Если водитель долго не присылает координаты, сервис запрашивает их через Push Service.

## Запуск

Нужны Go 1.26+, Docker и релизный `tripgoctl` из курса.
Для проверки кода также нужен `golangci-lint` v2 в `$(go env GOPATH)/bin`.

```bash
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
make migrate
make run
```

Команды выполняются из корня репозитория. `tripgoctl` создаёт `.env` с настройками
окружения. Остальные переменные описаны в [.env.example](.env.example).
Файл `.env` в Git не добавляется.

По умолчанию сервис работает на `localhost:8080`:

```bash
curl -i localhost:8080/health
curl -i localhost:8080/ready
```

`/health` проверяет, что сервер работает, `/ready` — что доступна база.

HTTP-таймауты задаются через env: `HTTP_READ_TIMEOUT=10s`,
`HTTP_READ_HEADER_TIMEOUT=5s`, `HTTP_WRITE_TIMEOUT=10s`, `HTTP_IDLE_TIMEOUT=60s`.
Если переменная отсутствует, используется указанное значение по умолчанию;
нулевые, отрицательные и невалидные значения отклоняются при запуске.

Если `tripgoctl` выдаёт `embedded Push Service binary is absent`, нужна релизная
сборка со встроенной заглушкой пушей. При сборке из исходников `course-infra`
это цель `make build-tripgoctl-embedded`, а не обычный `go install`.

## API

| Метод | Путь | Действие |
|---|---|---|
| POST | `/api/v1/trips` | Создать поездку |
| GET | `/api/v1/trips/{tripId}` | Получить поездку |
| POST | `/api/v1/trips/{tripId}/finish` | Завершить поездку |
| POST | `/api/v1/trips/{tripId}/positions` | Сохранить координату |
| GET | `/api/v1/trips/{tripId}/positions` | Получить маршрут |

Форматы запросов и ответов — в [OpenAPI-контракте](contracts/openapi/trip-service.openapi.yaml).
Например, для активной поездки можно отправить точку и получить маршрут
(`TRIP_ID` — ID созданной поездки):

```bash
curl -i -X POST "localhost:8080/api/v1/trips/$TRIP_ID/positions" \
  -H 'Content-Type: application/json' \
  -d "{\"coordinates\":{\"latitude\":59.93,\"longitude\":30.33},\"recorded_at\":\"$(date -u +%FT%TZ)\"}"

curl -sS "localhost:8080/api/v1/trips/$TRIP_ID/positions"
```

Маршрут отсортирован по `recorded_at`, затем по `id`. Запоздавшие точки сохраняются,
но не уменьшают `last_position_at`: для этого используется `GREATEST` в SQL.
Точка и время последней координаты записываются в одной транзакции.
В завершённую поездку добавить координаты нельзя.

## Опрос устаревших поездок

Сканер → очередь → воркеры → Push Service.

Раз в 30 секунд сканер выбирает из БД активные поездки без свежих координат.
Если точек ещё не было, время считается от начала поездки. Найденные поездки
попадают в ограниченную очередь, откуда их забирают воркеры и отправляют
`REQUEST_POSITION` водителю.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `POSITION_CHECK_INTERVAL` | `30s` | Интервал проверки |
| `POSITION_STALE_AFTER` | `60s` | Сколько ждать координату |
| `POSITION_WORKERS` | `4` | Количество воркеров |
| `POSITION_QUEUE_SIZE` | `100` | Максимальный размер очереди |
| `POSITION_SCAN_BATCH_SIZE` | `100` | Размер порции при чтении из БД |
| `PUSH_HTTP_URL` | Из `.env` | Адрес Push Service |
| `PUSH_REQUEST_TIMEOUT` | `1s` | Таймаут запроса координаты |
| `SHUTDOWN_TIMEOUT` | `10s` в `.env` | Время на остановку сервиса |

Выборка читается порциями, без `OFFSET`, с продолжением по паре
`(COALESCE(last_position_at, started_at), id)`. Первый `dropped`, включая
вытеснение, останавливает обход; после полного батча сканер также останавливается,
если очередь заполнена. Следующий тик начинает обход заново.
В памяти находится только один батч, а не вся выборка.

Очередь приоритетная: сначала обрабатываются
поездки с самой старой координатой. Если очередь заполнена, более старая задача
вытесняет более свежую. Отброшенные задачи учитываются в `dropped` и пишутся
в лог с уровнем `Warn`. Сканер при этом не ждёт освобождения очереди.

Повторно поставить одну поездку не даёт map под mutex. Когда приходит координата,
ожидающая задача удаляется из очереди. Уже начавшийся запрос не отменяется.
Если устройство не ответило, поездка снова попадёт в выборку на следующем тике.
У воркера одна попытка отправки, без ретраев.

Очередь реализована через min-heap и `sync.Cond` под общим mutex с map.
Добавление, извлечение и отмена занимают `O(log N)`. Только при переполнении
самая свежая ожидающая задача ищется за `O(N)`, где `N` ограничено
`POSITION_QUEUE_SIZE`; выполняющиеся задачи не вытесняются.

При остановке сначала завершаются HTTP-запросы, потом сканер и воркеры.
Воркеры разбирают остаток очереди в пределах `SHUTDOWN_TIMEOUT`, после чего
оставшиеся вызовы отменяются. Клиент Push Service и база закрываются последними.

Код опроса находится в `internal/worker/positions`, HTTP-клиент —
в `internal/gateway/push`. Для выборки поездок есть отдельный индекс.

## Структура

- `cmd/trip-service` — запуск и сборка зависимостей.
- `internal/httpserver` — HTTP-обработчики.
- `internal/usecase` и `internal/domain` — логика работы с поездками.
- `internal/repository` и `internal/txmanager` — запросы к БД и транзакции.
- `internal/infra/telemetry` — логи, метрики и трейсы.
- `migrations` — миграции goose.

## Проверки

```bash
make test
make test-integration
make lint
go test -race -count=2 ./...
```

Для интеграционных тестов нужны запущенное окружение и применённые миграции.
Они создают свои поездки и удаляют их после проверки. Unit-тесты работают без БД.
В тестах пула тикер подменяется, гонки проверяются через `-race`, утечки горутин —
через `goleak`.
Отдельные тесты проверяют 250 поездок в трёх батчах по 100, одинаковые временные
метки на границе страниц, приоритет, вытеснение и конкурентную отмену.

`make generate` обновляет код из OpenAPI и gomock-моки,
`make generate-mocks` — только моки.

Адреса Grafana и Jaeger выводит `tripgoctl connect`. Логи сервиса пишутся в JSON,
метрики и трейсы отправляются через OpenTelemetry.
Гистограмма `tripgo.stale_checks.rows_read` записывает число строк, прочитанных за тик
(в Prometheus — `tripgo_stale_checks_rows_read_*`). Переполнение и вытеснение
увеличивают и `tripgo.stale_checks{result=dropped}`, и
`tripgo.position_requests{result=dropped}`, но не длительность HTTP-вызовов.
Отмена ожидающей задачи по пришедшей координате увеличивает
`tripgo.position_requests{result=cancelled}`, но не попадает в длительность вызовов
Push Service. Уже начавшийся запрос учитывается по его результату: `success` или `error`.
Gauge `tripgo.trips.active` при сборе метрик читает число активных поездок из БД,
поэтому корректен и после перезапуска сервиса.
