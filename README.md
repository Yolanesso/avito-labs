
# Trip Service

Это учебный сервис для работы с поездками.

Сервис умеет:

* создавать поездку;
* получать поездку по ID;
* завершать поездку;
* проверять работу сервиса и базы данных.

Данные хранятся в PostgreSQL.

## Запуск окружения

Для работы нужны Docker и `tripgoctl`.

Запуск окружения:

```bash
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
```

После запуска будет создан файл `.env` с адресами PostgreSQL и коллектора
телеметрии. Файл локальный: его не добавляем в Git.

## Миграции

Применить миграции:

```bash
make migrate
```

Посмотреть их состояние:

```bash
make migrate-status
```

Откатить последнюю миграцию:

```bash
make migrate-down
```

В проекте создаются две таблицы:

* `trips` — поездки;
* `trip_status_history` — история изменения статусов.

## Запуск сервиса

```bash
make run
```

Сервис запускается на порту `8080`. Для второй лабораторной в
`environment.toml` включены PostgreSQL и observability.

## Проверки

```bash
make lint              # линтер и форматирование
make test              # обычные тесты, проверка гонок и покрытие
make test-integration  # тесты репозитория с настоящей базой
```

Перед интеграционными тестами нужны `tripgoctl environment start` и
`make migrate`. Тесты создают свои поездки и убирают их после проверки;
повторный запуск не требует очистки базы.

## Генерация кода

Часть Go-кода генерируется из OpenAPI-контракта.

```bash
make generate
```

Сгенерированный файл:

```text
internal/generated/api.gen.go
```

Его не нужно изменять вручную.

Моки для тестов действий создаются отдельно:

```bash
make generate-mocks
```

Файлы `mocks_test.go` создаёт `mockgen`; их добавляем в коммит вместе с тестами.

## Переменные окружения

В работе используются:

* `HTTP_ADDR` — адрес HTTP-сервера;
* `LOG_LEVEL` — уровень логирования;
* `SHUTDOWN_TIMEOUT` — время ожидания при остановке;
* `DATABASE_URL` — адрес PostgreSQL;
* `DATABASE_MAX_CONNS` — максимальное число соединений;
* `DATABASE_MIN_CONNS` — минимальное число соединений;
* `DATABASE_MAX_CONN_LIFETIME` — время жизни соединения;
* `DATABASE_CONNECT_TIMEOUT` — таймаут подключения;
* `DATABASE_QUERY_TIMEOUT` — таймаут SQL-запроса.
* `OTEL_SERVICE_NAME` — имя сервиса в телеметрии;
* `OTEL_EXPORTER_OTLP_ENDPOINT` — адрес коллектора;
* `OTEL_EXPORTER_OTLP_PROTOCOL` — протокол (`http/protobuf`);
* `OTEL_TRACES_SAMPLER` — правило выборки трейсов.

Пример находится в `.env.example`.

## HTTP-запросы

Проверка работы процесса:

```bash
curl -i localhost:8080/health
```

Проверка доступности базы:

```bash
curl -i localhost:8080/ready
```

Создание поездки:

```bash
curl -i -X POST localhost:8080/api/v1/trips \
  -H 'Content-Type: application/json' \
  -d '{
    "user_id": "5cb72c04-7650-45c9-a79b-bcdba0631e0c",
    "driver_id": "8860b315-ec86-42eb-a17c-7c163d721ff5",
    "start_point": {
      "latitude": 59.9398,
      "longitude": 30.3146
    },
    "end_point": {
      "latitude": 59.929,
      "longitude": 30.3626
    },
    "price": 1450
  }'
```

Получение поездки:

```bash
curl -i localhost:8080/api/v1/trips/<trip-id>
```

Завершение поездки:

```bash
curl -i -X POST \
  localhost:8080/api/v1/trips/<trip-id>/finish
```

## Решения

### Архитектура

Путь одного запроса: HTTP-ручка в `internal/httpserver/trip/create`,
`get` или `finish` вызывает `internal/service` (тонкую обёртку для
совместимости), затем действие из
`internal/usecase/trip/create`, `get` или `finish`. Действие вызывает
`internal/repository`, а репозиторий обращается к PostgreSQL.
Доменная модель и правило завершения поездки находятся
в `internal/domain/trip`: домен не импортирует HTTP, базу или телеметрию.

У каждого действия свой узкий интерфейс репозитория в его `contract.go`:
например, получению поездки нужен только `GetByID`. Старая обёртка
`internal/service` пока сохраняет общий интерфейс для существующих тестов.
Интерфейс сервиса для каждой HTTP-ручки — в её `contract.go`.
Они нужны, чтобы тестировать слои с моками,
не поднимая базу и HTTP-сервер. Конкретные реализации соединяются в
`cmd/trip-service/main.go`; фреймворка для внедрения зависимостей нет.

В `internal/httpserver` остались роутер, общие health/ready и короткие методы,
которые передают вызов в пакет нужной ручки. Общие функции ответа и конвертации
лежат в `internal/httpserver/response`. Название `httpserver` сохранено, чтобы
не конфликтовать со стандартным пакетом `net/http`.

Модели `internal/model` — переходные алиасы на `internal/domain/trip`, чтобы
старый код репозитория и транспорта не пришлось переписывать целиком.

### Логи, метрики и трейсы

Логи пишутся в JSON через `slog`. У HTTP-запроса есть метод, шаблон маршрута,
статус, время ответа и, если запрос попал в трейс, `trace_id` и `span_id`.
После успешного сохранения поездки отдельно логируется `trip created` или
`trip completed` с `trip_id` и тем же `trace_id`. Ошибки клиента (4xx) дают
лог уровня Info, ошибки сервиса (5xx) — Error. Тела запросов и ответов не
логируются.

Middleware идут в порядке `Recover → Tracing → Logging → Metrics → роутер`.
`Recover` перехватывает панику и отвечает 500. Трейс связывает HTTP-запрос и
SQL-запросы, а для ошибок HTTP-спан получает статус Error. На уровне пула
PostgreSQL подключён `otelpgx`. Метрики и трейсы отправляются в коллектор по
OTLP; при его недоступности обычные запросы к сервису продолжают работать.

Есть метрики длительности HTTP и SQL, текущего числа HTTP-запросов, числа
созданных и завершённых поездок. Для `http.route` используется шаблон вроде
`/api/v1/trips/{tripId}`, иначе каждый UUID создал бы отдельный ряд метрик.

Проверка руками: запусти `make run`, создай и заверши поездку, возьми
`trace_id` из JSON-лога и найди его в Jaeger. Внутри HTTP-спана должен быть
SQL-спан. В Grafana найди метрики `http_server_request_duration_seconds_count`
и `tripgo_trips_created_total`. Адреса Jaeger и Grafana показывает
`tripgoctl connect`; скриншоты приложи к описанию PR.

### Транзакции

Используется уровень изоляции `Read Committed`.

Создание поездки состоит из двух запросов:

1. запись поездки в `trips`;
2. запись статуса в `trip_status_history`.

Оба запроса выполняются в одной транзакции. Если один из них завершится с ошибкой, изменения отменятся через `ROLLBACK`. Если ошибок нет, выполняется `COMMIT`.

Транзакция хранится в `context`. Repository берёт её оттуда. Если транзакции нет, repository использует обычный пул соединений.

Если `Do` вызывается внутри другого `Do`, новая транзакция не создаётся.

### Один водитель и одна активная поездка

В PostgreSQL создан уникальный индекс:

```sql
CREATE UNIQUE INDEX trips_one_active_per_driver_idx
ON trips (driver_id)
WHERE status = 'active';
```

Он запрещает создавать две активные поездки одному водителю.

При нарушении индекса PostgreSQL возвращает ошибку `23505`. Сервис преобразует её в ответ `409 driver_busy`.

### Завершение поездки

Поездка завершается только при статусе `active`:

```sql
WHERE id = $1 AND status = 'active'
```

Поэтому при двух одновременных запросах поездку завершит только один из них. Второй получит ошибку `409 trip_completed`.

### Health и Ready

`/health` проверяет, что процесс сервиса работает. В базу этот запрос не ходит.

`/ready` проверяет PostgreSQL. Если база остановлена, он возвращает `503`.

### Остановка сервиса

Сервис обрабатывает `SIGINT` и `SIGTERM`.

При остановке он перестаёт принимать новые запросы и ждёт завершения текущих запросов. Время ожидания задаётся через `SHUTDOWN_TIMEOUT`.
